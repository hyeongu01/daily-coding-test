# solution-review — 풀이 평가 · 개선 제안

사용자가 "다 풀었어", "풀었어", "리뷰해줘" 라고 하면 이 스킬을 쓴다. 목적은 코딩테스트 역량을 서서히 끌어올리는 것이다. 정답을 대신 써 주는 게 아니라, 사용자가 **스스로 다시 시도해 볼 수 있게** 방향만 준다.

## 흐름

1. **대상 파일 찾기**
   - 사용자가 파일을 말했거나 IDE 에서 열어 둔 파일이 있으면 그 파일.
   - 없으면 가장 최근 수정된 `src/y*/m*/D*.java` (오늘 날짜 `D{dd}_*` 우선).
   - `TODO(daily-problem)` 마커가 남아 있으면 아직 풀이 전이다. 지우고 오라고 알리고 평가하지 않는다.
1-1. **키워드 공개**: 추천 스캐폴드는 풀기 전 스포일러를 막으려고 `키워드:` 줄 없이 만든다. 파일에 `키워드:` 줄이 없으면 javadoc 링크 줄 아래에 ` * <p>` + ` * 키워드: <태그들>` 을 추가한다. 태그는 `python -I .claude/skills/daily-problem/scripts/profile.py list` 에서 해당 id 의 태그(추천 시 기록한 것)를 쓰고, 사용자가 실제로 쓴 접근이 다르면 그것도 덧붙인다. 채팅 평가 맨 앞에 "이 문제의 키워드: …" 로 알려 준다. 이미 `키워드:` 줄이 있으면 건드리지 않는다.
2. **풀이 반영**: `python -I .claude/skills/daily-problem/scripts/profile.py sync` 로 프로필에 solved 를 먼저 반영한다. 풀이 시간·체감 난이도를 말했으면 `record --result solved --id <id> --minutes N --note "..."` 로 남긴다(같은 날 같은 결과는 기존 이력에 합쳐진다). 시간은 사용자가 말하지 않으면 파일 생성~마지막 저장 시각(`stat`)으로 추정하고 추정치라고 밝힌다.
3. **코드 읽기 + 테스트 확인**: 파일 전체를 읽는다. 가능하면 javac 로 컴파일·실행해 `TestRunner` 가 전부 통과하는지 확인한다(실행이 어려우면 코드로 추적하고 그렇다고 밝힌다). 문제의 예시 외 엣지 케이스(빈 입력, 1개, 전부 같은 값, 최대 크기, 오버플로 등)를 머릿속으로 돌려 본다.
4. **평가** — 아래 항목을 근거와 함께 쓴다. 칭찬도 구체적으로(무엇이 왜 좋은지).
   - **정확성**: 통과 여부, 놓친 엣지 케이스.
   - **복잡도**: 시간·공간을 O(·) 로, 그렇게 되는 이유(분할 상환 등)와 함께. 제한 조건(입력 크기)에 비춰 충분한지.
   - **자료구조/알고리즘 선택**: 이 문제에 적절한가. 실제로 쓴 방식을 정확한 이름으로(예: `Deque` 를 스택처럼 썼다면 "단조 스택").
   - **가독성/코드 품질**: 변수명, 불필요한 코드, 중복, 자바 관용구, 주석의 정확성.
5. **개선 사항**: 지금 풀이를 고친다면 무엇을 바꿀지 구체적으로(줄/구문 단위). 없으면 "개선할 점 없음"이라고 쓰고 억지로 만들지 않는다.
6. **더 좋은 방향 제안**: 더 효율적이거나 더 간결하거나 패턴이 다른 접근이 있으면 제안한다. 없으면 "현재 풀이가 이미 최적 수준"이라고 쓴다.
   - **완성 코드를 주지 않는다.** 접근 이름, 핵심 아이디어 한두 문장, 시도해 볼 때의 포인트(뭘 바꿔 보면 되는지)만 준다. 사용자가 "코드도 보여 줘"라고 하면 그때 준다.
   - 현재 수준보다 한 단계 안쪽의 시도 거리로 한다(난이도를 서서히 올리는 원칙). 예: 인덱스를 쌓는 단조 스택 ↔ 값을 쌓는 단조 스택 비교, 배열 스택으로 직접 구현해 보기.
   - 같은 패턴을 연습할 만한 다음 문제가 떠오르면 한 줄로 덧붙인다(추천 확정은 daily-problem 이 한다).
7. **채팅 출력**: 아래 형식을 간결하게.
8. **파일에 기록**: 풀이 파일 맨 위 javadoc 에 "풀이 평가" 블록을 추가한다(아래 규칙).

## 채팅 출력 형식

```
## 풀이 평가 — <문제명>
**총평**: 한두 문장 (통과 여부 + 핵심)
- 정확성: ...
- 복잡도: 시간 O(·) / 공간 O(·) — 이유
- 자료구조/알고리즘: ...
- 가독성: ...

**개선 사항**
1. ...

**이렇게도 풀어 보세요**
- <접근 이름>: 핵심 아이디어 / 시도 포인트
```

## 풀이 파일에 남기는 규칙

- 위치: 클래스 바로 위 javadoc(`/** ... */`) 안, 기존 `키워드:` 줄 **아래**. javadoc 이 없으면 만든다. 파일에 이미 `풀이 평가` 블록이 있으면 새로 쌓지 말고 그 블록을 **교체**한다(같은 날 재평가 시). 다른 날 다시 풀어 평가하는 경우는 날짜를 달리해 아래에 추가한다.
- 형식:

```java
/**
 * [프로그래머스 - 뒤에 있는 큰 수 찾기]
 * <p>
 * https://school.programmers.co.kr/learn/courses/30/lessons/154539
 * <p>
 * 키워드: 스택, 단조 스택
 * <p>
 * 풀이 평가 (2026-11-20)
 * - 총평: ...
 * - 복잡도: 시간 O(N) / 공간 O(N)
 * - 개선: ...
 * - 다음에 시도: ...
 */
```

- 한 줄 80자 안팎으로 줄을 나눠 쓴다. 코드 블록·긴 설명은 넣지 않는다(채팅에만).
- **`풀이 평가` 블록 안에 `자료구조:` / `알고리즘:` / `키워드:` 로 시작하는 줄을 쓰지 않는다.** daily-problem 의 태그 자동 추정이 그 줄을 읽기 때문이다. 링크(URL) 줄과 기존 `키워드:` 줄은 건드리지 않는다.
- 풀이 코드 본문은 수정하지 않는다. 주석만 추가한다. 개선 제안을 코드에 반영하는 건 사용자가 요청할 때만.
- 수정 후 컴파일 가능한지 확인한다(주석만 바뀌었으니 `*/` 중복 같은 실수만 확인).

## 주의
- 평가는 솔직하게. 틀렸거나 비효율이면 그렇게 말하되, 무엇이 막혔을지·어떻게 접근하면 되는지를 같이 준다.
- 사용자가 직접 한 시도(개선안을 다시 풀어 온 경우)가 있으면 새 풀이와 이전 풀이를 비교해 무엇이 나아졌는지 말한다.
- 프로필 JSON 은 직접 편집하지 말고 `profile.py` 명령으로만 갱신한다.
